# 阵容路线（Daily Composition Routes）方案设计现状

> 更新时间：2026-09-21  
> 基线提交：`9f21f75 feat(routes): launch daily composition routes v1`  
> 文档用途：作为后续需求调整、算法修改、API 变更和页面改版的讨论基线。

## 1. 产品目标

阵容路线要回答的核心问题是：

1. 某职业在某个 Day 有哪些主流阵容；
2. 选择一套阵容后，真实 Run 在后续实际观测 Day 演变成了哪些方向；
3. 每个方向有多少真实 Run，占父阵容可继续观测样本多少；
4. 转型过程中保留、新增、退出了哪些核心卡；
5. 该方向有哪些真实代表阵容、常见变体和非核心关联牌。

它不是单卡生命周期，也不是完整卡组签名浏览器。设计目标是将大量逐日快照收敛为少量、可解释且有真实样本支持的阵容演变方向。

## 2. 当前统计口径

当前路线数据限定为：

- 当前赛季、当前 Phase；
- 传奇段位；
- 最终达到 10 胜的完整 Run；
- 每个 `Run / Day` 仅保留当天最后一次快照；
- 阵容归类使用物品存在性；
- 品质、附魔、槽位不参与阵容身份；
- 各职业独立构建；
- 一个统计版本只允许包含一个 `season / phase`。

页面阶段划分：

- 前期：Day 1–3；
- 中期：Day 4–7；
- 后期：Day 8–11；
- 大后期：Day 12+。

阶段只用于页面组织；事实层仍保留逐 Day 数据和真实跨日关系。

## 3. 数据事实层

### 3.1 每日最终阵容

源快照标准化后形成 `final_compositions`：

```text
run_id + day
→ 当日最后一次快照
→ 物品集合 item_signature
```

配套表 `final_composition_cards` 保存该快照中的卡牌明细。

### 3.2 缺失 Day 的处理

同一 Run 只连接相邻的“实际观测点”，不插值：

```text
Day 3 → Day 4
Day 3 → Day 5  # Day 4 缺失时允许，stage_gap=1
```

缺失 Day 不代表失败、停留或未转型。

## 4. 每日阵容原型生成

### 4.1 互斥归类

每个职业、每个 Day 独立构建有上限的卡牌存在性决策树：

- 候选特征最多 32 张卡；
- 树深最多 3；
- 叶节点最多 6；
- 最小叶节点样本：`max(2, ceil(当日样本 × 8%))`；
- 分裂最低信息增益：`0.04`。

每个 Run/Day 只属于一个叶节点，因此每日阵容原型互斥，不会因频繁项集重叠而重复计数。

### 4.2 核心卡命名

节点名称不能用各张卡的边际频率直接拼接，必须审计完整核心集合的真实共同出现率。

当前规则：

1. 单卡在节点内出现率至少 20% 才进入候选池；
2. 候选池最多 16 张；
3. 枚举 2–5 张组合；
4. 组合必须在至少 50% 的节点成员 Run 中完整共现；
5. 优先选择尺寸更大的合格组合；同尺寸优先共同支持数更高者；
6. 没有合格多卡组合时降级为支持率至少 50% 的真实单核心；
7. 仍无合格核心时记录为空核心/分散构筑，不强行命名。

节点持久化：

- `core_items`；
- `core_support_runs`；
- `core_support_rate`；
- `representative_items`：节点内出现率至少 35% 的前 8 张卡，仅用于描述，不等同核心。

公开页面目前只展示非空核心且 `core_support_rate >= 50%` 的节点；分散构筑仍存在于统计事实和分母中。

## 5. 原始路线边

同一 Run 的相邻实际观测节点形成一条原始边：

```text
(parent_day, parent_node)
→ (child_day, child_node)
```

每条边保存：

- `run_count`：真实经过该边的 distinct Run；
- `parent_runs`：父阵容全部 Run；
- `parent_observable_runs`：父阵容中存在下一次实际观测的 Run；
- `continuation_rate = parent_observable_runs / parent_runs`；
- `transition_rate = run_count / parent_observable_runs`；
- `stage_gap = child_day - parent_day - 1`。

同一个父节点的不同目标 Day 共用同一个 `parent_observable_runs`，防止跨缺失 Day 的分支概率合计超过 100%。

每条边的真实成员写入 `daily_archetype_edge_members`，以支持真实代表阵容、关联牌和后续审计。

## 6. 展示方向的筛选与合并

页面不是完整原始边浏览器。原始边会进一步收敛为最多三个差异方向。

### 6.1 动态展示门槛

每个父阵容的门槛：

```text
minimum_runs = min(15, max(3, ceil(parent_observable_runs × 3%)))
```

低于门槛的原始边不展示，但仍保留在原始可观测分母中；可见方向不会重新归一化。

### 6.2 方向身份

方向主要由目标核心组成定义。两个核心集合 `A`、`B` 的相似度：

```text
containment(A, B) = |A ∩ B| / min(|A|, |B|)
```

达到 80% 时合并为同一方向：

- 可跨不同目标 Day 合并；
- 按样本最多的候选优先建立代表；
- 后续候选只与该代表核心比较；
- 不使用传递闭包，避免 `A≈B、B≈C` 被误扩成 `A≈C`。

### 6.3 展示数量与覆盖率

- 合并后按 distinct 样本量排序；
- 每个父阵容最多展示 3 个方向；
- 不足 3 个不补；
- 方向样本数是所含原始边样本数之和；
- 三个可见方向相对原始 `parent_observable_runs` 计算总覆盖率。

页面解释：

- 覆盖率 ≥ 70%：路线较集中；
- 50%–70%：存在多种发展方向；
- < 50%：构筑较为分散，主要方向仅供参考。

## 7. 方向详情

每个可见方向提供：

### 7.1 到达 Day 分布

合并跨 Day 变体后，仍展示各真实目标 Day 的样本和占方向样本比例。

### 7.2 常见目标变体

最多展示 5 个原始目标节点变体，包括：

- 目标核心；
- 到达 Day；
- 样本数；
- 在方向内部的占比。

### 7.3 真实代表阵容

代表阵容必须来自方向边成员的真实 Run/Day 快照，禁止统计拼装。

当前选择逻辑偏向：

1. 覆盖更多高频非核心关联牌；
2. 包含更少无关噪声牌；
3. 卡组信息较完整；
4. 在其他条件一致时采用稳定排序。

API 返回 `representative_run_id`、`representative_day` 和完整代表阵容卡牌。

### 7.4 非核心关联牌

在方向真实目标快照中，排除目标核心后统计：

```text
minimum_association_support = max(3, ceil(direction_observations × 10%))
```

按出现 Run 数排序，最多展示 8 张，并显示分子、分母和支持率。

### 7.5 核心变化

页面根据父核心和方向代表目标核心展示：

- 保留核心；
- 新增核心；
- 退出核心。

## 8. 持久化模型

当前统计库 schema 版本为 5，主要表：

- `build_versions`：不可变统计版本元数据；
- `final_compositions`、`final_composition_cards`：每 Run/Day 最终快照；
- `daily_archetype_nodes`：每日互斥阵容节点；
- `daily_archetype_cards`：节点核心、常见和变体卡；
- `daily_archetype_members`：节点真实 Run 成员；
- `daily_archetype_edges`：原始实际观测转型边；
- `daily_archetype_edge_members`：边的真实 Run 成员；
- `daily_archetype_edge_cards`：边上的保留、新增、移除卡统计。

库按不可变 `version_id` 构建，发布器负责候选库校验和替换，避免直接在生产库上原地构建。

## 9. API 与页面

公开 API：

- `GET /api/routes/latest`：最新统计版本及样本元数据；
- `GET /api/routes/daily/summary?hero=...`：职业各 Day 可展示节点摘要；
- `GET /api/routes/daily?hero=...&day=...`：某职业某 Day 的节点、原始边和收敛后的方向；
- `GET /api/routes/cores`；
- `GET /api/routes/cores/<core_id>`：保留的早期核心路线兼容接口。

页面入口：`/routes`。

当前交互：

```text
选择职业
→ 选择 Day
→ 选择当日主流阵容
→ 查看最多三个后续方向
→ 展开真实代表阵容、关联牌、变体和到达 Day
→ 可跳转 /runs 查询相似真实阵容
```

卡牌使用与 `#bz db` 同源的卡图和中文名，并按 Small/Medium/Large 保持比例。

## 12. 当前已知边界

1. **成功样本偏差**：当前只分析传奇 10 胜 Run，描述的是成功路线，不代表所有玩家或全部 Run 的自然分布。
2. **目标方向是下一次实际观测**：跨 Day 分支可能是中间快照缺失，不等于玩家直接跳过若干 Day。
3. **节点划分是统计原型**：决策树叶节点用于互斥归类，核心卡用于解释；两者不是完整卡组定义。
4. **最多三个方向是产品收敛**：低样本或第四名以后的路线仍在分母，但主页面不展示。
5. **近似合并依赖 80% 包含率**：对一张核心和两张核心的包含关系较宽松，未来需求调整时需重点审视。
6. **方向样本当前按原始边数量求和**：在正常的下一观测边模型中同一父节点的 Run 只落入一条边；若未来允许多目标窗口，必须改为 distinct `run_id` 去重。
7. **代表阵容是算法选出的真实样本**：它不是人工推荐，也不保证是该方向胜率最高的阵容。
8. **关联牌是共现描述而非因果推荐**：出现率高不表示加入该卡会提高胜率。
9. **Day 快照完整度影响路线质量**：缺失和重试失败会减少可观测分母并增加跨日边。
10. **历史版本归档策略**：新版本上线后历史版本数据归档到 COS，不在线回填。

## 13. 后续需求变更的决策清单

提出新需求时，建议逐项确认：

1. 数据 cohort 是否仍限定传奇 10 胜；
2. 起点是“某个 Day 阵容”还是“前期核心”；
3. 路线连接下一实际观测、固定下一 Day，还是阶段终点；
4. 阵容身份继续由目标核心决定，还是引入完整卡组相似度；
5. 动态门槛公式是否改变；
6. 隐藏分支是否继续计入原始分母；
7. 80% 包含率是否调整，单核心与多核心是否需要特殊规则；
8. 是否仍最多展示三个方向；
9. 跨不同目标 Day 是否继续合并；
10. 代表阵容的选择目标是“最典型”“最强”还是“最常见”；
11. 关联牌是否继续排除核心，以及分母采用方向 Run 还是目标快照；
12. 页面是继续逐 Day 浏览，还是增加一条可连续展开的完整路线视图；
13. 新需求是否需要新增 schema 字段、重建统计库和提升 schema 版本；
14. 是否需要保留现有 API 向后兼容。

## 14. 已确认的下一版方案修改（待实现）

以下需求已经确认，作为下一版设计基线；当前尚未实现、未提交、未部署。

### 14.1 节点自身的当天阵容榜与关联牌榜

当前页面将“真实代表阵容”和“关联牌”绑定在从父节点通往下一观测节点的方向上，展示的是后续目标 Day 的实际阵容。这不符合新的产品语义。

下一版调整为：

- 每个阵容节点拥有自己的**当天推荐阵容排行榜**和**当天关联牌排行榜**；
- 点击 Day N 节点时，详情查询 Day N 节点自身，不再查询 Day N→Day N+1 边的目标阵容；
- 两个排行榜均使用该职业、该 Day、该节点的**全局成员 Run**，不因用户从哪条路径到达而改变；
- 路径样本只影响后续分支概率，不影响节点详情排行榜口径；
- 删除“查询相似真实阵容”跳转，节点详情不再引导到 `/runs`。

画布节点保持简洁，只展示核心卡和必要统计；完整排行榜放在节点详情侧栏。

#### 当天推荐阵容榜

默认展示 Top 3。

聚合口径：

1. 所有候选必须来自节点成员的真实当天快照，禁止统计拼装；
2. 候选快照必须完整包含该节点的全部核心卡；未完整包含核心的节点成员不进入推荐阵容榜，但仍保留在节点全局样本和关联牌统计分母中；
3. 推荐榜中的核心身份固定为该节点核心，不按单条快照重新推断；
4. 排除核心后的非核心物品集合使用 Jaccard 相似度：

```text
Jaccard(A, B) = |A ∩ B| / |A ∪ B|
```

5. 非核心 Jaccard 相似度达到 60% 时合并为同一个推荐阵容簇；
6. 合并过程需要采用稳定、可解释且不产生传递链误合并的代表比较策略；
7. 阵容簇按覆盖的 distinct Run 数降序排列；
8. 簇内按完整物品集合统计真实快照频次，选择出现次数最多的真实完整阵容作为代表；并列时使用稳定的卡牌 ID 排序；
9. 每个榜单条目展示代表卡组、阵容簇覆盖局数和节点内占比；
10. 品质、附魔和槽位不参与阵容簇身份，卡图仍按卡牌原始 Size 展示。

推荐阵容榜分母为该节点全部全局成员 Run：

```text
recommendation_rate = cluster_distinct_runs / node_global_runs
```

#### 当天关联牌榜

默认展示 Top 8。

统计口径：

- 完全排除节点核心卡；
- 在节点全部全局成员 Run 中按卡牌存在性统计；
- 同一 Run 中同一卡牌只计一次；
- 按出现率降序，出现率相同时按出现局数和稳定 card ID 排序；
- 每张牌展示原图、名称、出现局数和节点内出现率。

```text
association_rate = card_distinct_runs / node_global_runs
```

关联牌榜是当天节点内的共现描述，不宣称因果增益或胜率提升。

### 14.2 从每日独立面板改为连续分支树

当前交互以“选择一个 Day，再查看它下一步”为主，用户感知上更像每天独立统计，缺少连续路线。

下一版改为：

```text
选择职业与起始 Day 阵容
→ 画布生成该节点
→ 默认只展开严格下一 Day
→ 点击任一后续节点
→ 沿该路径样本继续展开再下一 Day
→ 形成可交互的连续分支树
```

关键规则：

- 路线只连接严格相邻 Day：`Day N → Day N+1`；
- 缺失下一 Day 快照的 Run 不参与该层路线分母和分支；
- 不再把 `Day 3 → Day 5` 作为画布路线边；
- 初次选定起点后只加载下一层，不一次性展开完整树；
- 用户点击节点时按需继续展开，避免画布一次加载过多数据；
- 后续分支必须沿用“从起点到当前节点”的路径成员继续收窄；
- 节点详情仍使用该节点的全局成员样本，与路径分支统计明确分开。

### 14.3 可拖动画布

页面主体改为类似流程图编辑器的路线画布：

- 支持鼠标或触控拖动画布；
- 支持缩放、适配视图和回到起点；
- 节点按 Day 分层，从左到右排列；
- 连线显示路径样本数、父路径可观测分母和转型率；
- 点击节点时高亮从起点到该节点的路径；
- 点击节点可打开详情侧栏，并可继续展开下一 Day；
- 已展开的分支保留在画布中，允许用户来回比较；
- 移动端需要支持触控拖动、双指缩放或等价控制按钮。

画布只负责“路线关系与核心识别”，详情侧栏负责“当天真实阵容和关联牌”，避免把大量卡图全部塞进节点造成不可读。

### 14.4 路径统计与节点统计双口径

下一版需要明确区分两类样本：

#### 节点全局样本

```text
该职业 + 该 Day + 归入该节点的全部 Run
```

用于：

- 节点当天样本数和当天出场率；
- 节点核心及完整核心共现率；
- 当天推荐阵容 Top 3；
- 当天非核心关联牌 Top 8；
- 节点详情。

#### 当前路径样本

```text
从用户选中的起点开始，依次经过当前已选路径全部节点的 Run 交集
```

用于：

- 从当前节点继续展开下一 Day；
- 下一层每个分支的样本数；
- 路径条件下的转型率；
- 画布连线宽度和标签。

因此，同一个全局节点从不同路径抵达时：

- 节点详情内容相同；
- 进入节点和离开节点的路径样本、概率可以不同；
- API 不能只按 `node_id` 返回后续边，必须携带路径上下文或路径成员标识。

### 14.5 分支数量

新画布不再限制每个节点最多三个方向。

规则调整为：

- 所有达到动态样本门槛的严格下一 Day 分支均可展示；
- 不设置固定 3 条或 5 条上限；
- 低于门槛的分支仍隐藏，但保留在该层原始分母中；
- 若真实数据产生过多可见分支，应通过画布布局、折叠、聚焦或“显示低占比分支”交互解决，而不是在统计层硬截取前三名；
- 动态门槛公式是否沿用当前 3% / 3–15 局，需要用新路径条件下的真实数据重新校准。

### 14.6 对现有设计的影响

继续有效：

- 每 Run/Day 最后快照；
- 每日互斥阵容节点；
- 核心完整共现审计；
- 隐藏分支保留在原始分母；
- 真实阵容禁止统计拼装；
- 节点核心相似性仍可用于节点定义或视觉提示。

需要替换或重做：

- “下一次实际观测 Day”路线边改为严格相邻 Day；
- 方向详情中的目标 Day 代表阵容改为节点自身当天的推荐阵容榜和关联牌榜；
- 删除“查询相似真实阵容”跳转；
- 最多三个方向取消；
- 以每日独立查询为中心的页面交互改为状态化分支树；
- 当前 `directions` 响应不足以支持路径条件展开，需要新增路径查询契约；
- 代表阵容和关联牌应从边成员统计迁移为节点成员统计；
- 当前跨 Day 合并与到达 Day 分布不再是主画布核心能力，可保留为分析数据或移出主流程。

### 14.7 预计数据与 API 改造

建议拆为两个 API 层次：

1. **节点详情 API**：按 `version + hero + day + node_id` 返回全局节点详情、当天代表阵容和当天关联牌；
2. **路径展开 API**：接收起点和当前路径节点序列，基于路径成员交集返回严格下一 Day 的全部合格分支。

路径展开响应至少包含：

- 当前路径的 distinct Run 数；
- 当前路径中有 Day N+1 快照的可观测 Run 数；
- 每个子节点的路径成员 Run 数；
- `transition_rate = child_path_runs / path_observable_runs`；
- 隐藏分支样本数和可见分支总覆盖率；
- 子节点的全局基础信息，供画布渲染。

实现时应避免把大量 `run_id` 下发给浏览器。路径上下文可采用服务端签名路径描述、稳定节点序列或短期缓存 token，具体方案需通过性能和可复现性评估后确定。

## 15. 已确认细节与待确认项

已确认：

1. 动态门槛沿用 `min(15, max(3, ceil(path_observable_runs × 3%)))`；
2. 同一个全局阵容节点从不同父路径抵达时，画布合并为一个节点，由多条父路线汇入；
3. 合并节点只展示一份全局节点详情，但每条进入连线保留各自的路径样本数、可观测分母和转型率；
4. 从合并节点继续展开时，汇总所有已进入该节点的路径成员，按 `run_id` 去重后作为当前路径样本；不会只沿最后点击的单条入边继续计算。

仍需确认：

1. 是否允许用户收起某个节点后续分支；
2. 是否需要“返回上一步”和路径面包屑；
3. 详情侧栏是否同时展示节点全局样本与当前路径样本作对照；
4. 画布技术方案采用现有代码内自研 SVG/HTML，还是引入成熟流程图库；
5. 分享图是截取当前画布视图，还是生成固定布局的路线摘要图。

## 16. 修改流程与发布闸门

后续改动按以下顺序执行：

1. 将新需求写成明确口径和验收例子；
2. 标记哪些旧设计继续有效、哪些失效；
3. 先补失败测试，再修改算法；
4. 在真实生产库只读副本上校准，不凭合成数据宣布完成；
5. 若数据模型变化，提升 schema 版本并构建隔离统计库；
6. API 契约和兼容测试通过后再改页面；
7. 完成桌面与移动端真实浏览器验收；
8. 独立审查和 staging 完成后，必须先提供一个用户可访问的候选页面地址，由用户亲自验收最终画布效果；
9. 用户未明确确认页面效果通过前，不得部署或替换生产版本；
10. 用户确认后，再执行生产备份、部署和公网验收，并将技术验收结果与用户视觉验收分开汇报。
