## 已确认的证据

- 生产 Web 日志 `/opt/qiubot/web_runs/logs/app.log`：北京时间 20:00:56 起采集入库出现连续 500，20:01–20:15 的职业概况、阵容榜、对局查询也出现 500。
- 对局库 `/opt/qiubot/data/bazaar_runs.db` 实测为 `journal_mode=delete`；统计库 `stats.db` 为 `wal`。不能将统计库的 WAL 配置视为对局库已经配置。
- 统计日志中失败的对局查询有约 5 秒等待，符合读取连接的 SQLite 锁等待上限。
- 后台阵容分析 `_build()` 在遍历数据库游标时逐行解析、计算原始数据，在整个遍历期间保留读取锁。
- `/api/ingest` 在 SQLite 写事务中逐条调用 Redis；数据库异常被逐条吞掉，提交异常分支没有保证回滚和关闭连接。
- 只读核对时，当前阶段数据库有 81,782 条记录，胜率 Redis 列表有 82,080 条，多出 298 条。这证实缓存与已提交记录不一致；提交前更新缓存是可以复现的污染路径，但不能据此判定所有差额都来自本次事件。

DELETE 模式下，长读取会阻止写事务完成提交；等待提交的写连接又会阻止后续读取。Redis 调用和异常连接清理缺失会延长占锁时间。后台读取与采集重叠是符合日志和代码的触发路径；现有日志没有保存锁异常堆栈，无法断言当时最先持锁的是哪条 SQL。

## 修复内容

- Web 启动时启用并确认对局库使用 WAL；新阶段替换数据库后，服务重启也会重新配置。配置失败直接阻止启动，避免悄悄退回 DELETE 模式。
- 入库通过显式写事务和连接上下文保证成功提交、失败回滚，并在所有路径关闭连接。
- Redis、派生缓存和独立快照队列操作均在 SQLite 提交并关闭后执行。
- 数据库异常中止整批并记录堆栈；锁冲突返回可重试的 503 和 `Retry-After`。单条格式错误使用保存点回滚该条，避免留下半条数据或错误计数。
